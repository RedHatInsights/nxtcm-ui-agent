# HyperShell migration prep: Console Next UI agent

**Status: preparation only.** This document records the proposed Console Next migration for REHOR-182: both instance profiles — the Console Next UI agent and the Renovate (dep-master) agent — move to dispatcher-managed execution on the native OpenCode runtime. It does not authorize a cutover. No live resources were changed, and no runner or dispatcher image was promoted as part of this preparation.

## Scope and invariants

- Migrate both instance profiles to dispatcher-managed execution: the UI agent (jira-sprint workflow) and the Renovate dep-master agent (custom `renovate-fix` workflow). Leave the legacy [`deploy/template.yaml`](deploy/template.yaml), including its KEDA scaler, unchanged — cutover of the live deployments happens through GitOps, not this repository. The `renovate-fix` workflow logic is preserved: the Python preflight scripts are replaced by the registered TypeScript preflights from rehor #689, and the workflow guidance now has a native `AGENTS.md` (OpenCode) alongside the retained `CLAUDE.md`.
- Preserve the UI agent's existing GitOps-provided identity. The source of live overrides is the rendered app-interface entry `nxtcm-ui-agent` in `data/services/insights/platform-frontend-ai-dev/deploy.yml` (verified locally in GitOps): Jira label `hcc-ai-nxtcm`, board `Console Next Sprint Board`, sprint prefix `Console Next Sprint`, backlog `true` (the app-interface override wins; the template's `false` default must not override it), and the GitOps-supplied instance ID, config repo, and config path. The template defaults in [`deploy/template.yaml`](deploy/template.yaml) apply only when app-interface does not override them. Keep any credentials outside this repository and documentation.
- Preserve the legacy schedule: `America/New_York`, weekdays, 09:00–18:00. The legacy template's base replica setting is `0`, but its KEDA cron scaler raises the deployment to one replica during that window. A desired replica count of zero alone does not mean the legacy agent is inactive. Both profiles declare the same window as their dispatcher `schedule`, so dispatch replaces the KEDA scaling semantics like-for-like at cutover; outside the window the dispatcher skips the profile before any preflight runs.
- The Renovate (dep-master) profile migrates actively, not inert: it declares the registered TypeScript preflights `renovate-discover` then `renovate-pr-status` (rehor #689, in the `b7bfd8b` pin) with legacy-matching defaults. The order matters — `renovate-discover` populates the shared per-run task cache that `renovate-pr-status` reuses. `renovate-discover` is work-creating: a cycle with actionable failing Renovate PRs produces scripts and launches the sandbox; a quiet cycle returns `skip`/no scripts and starts nothing. The profile keeps its existing GitOps identity in `env` (the dispatcher validates the instance identity before evaluating the preflight list). The legacy Python preflight scripts and workflow files remain in place untouched for rollback; the dispatcher's preflight engine consumes the declarative `preflights:` field, never workflow scripts.
- The UI profile's native agents select role-based model tiers: the `console-next-coordinator` runs `gpt-6.1-sol` for coordination and complex reasoning, and the `frontend` subagent runs `gpt-6.1-terra` for substantial implementation work. The pinned coordinator creates the OpenCode session with the profile's root model and prompts without a model override, so the root model in `instance.yaml` is the coordinator's actual primary-session model, not just a fallback: it is `gpt-6.1-sol`, matching the coordinator agent's frontmatter selection. The `frontend` subagent's own frontmatter governs its child session and keeps `gpt-6.1-terra`; the title model follows the root selection. The pinned runner's packaged deployment defaults do not declare Sol, so [`instance/ui-config/opencode-deployment.json`](instance/ui-config/opencode-deployment.json) declares the instance-owned `rehor-openai` catalog (Sol, Terra, Luna, each with reasoning support and medium effort; no secrets — the gateway URL and token come from the deployment environment). No native role uses Luna; it stays declared only to preserve the packaged catalog surface. The Renovate profile migrates to the same native OpenCode runtime: `runtime: opencode`, `provider: rehor-openai`, root model `gpt-6.1-sol` (the `renovate-coordinator`'s primary-session model), and a native `frontend` subagent running `rehor-openai/gpt-6.1-terra` for the bounded code-fix and verification work. Like the UI profile, it declares the instance-owned catalog at [`instance/renovate-config/opencode-deployment.json`](instance/renovate-config/opencode-deployment.json) (Sol, Terra, Luna; no secrets — the gateway URL and token come from the deployment environment) via `BOT_CONFIG_PATH: instance/renovate-config`, with agent-level guidance in [`instance/renovate-config/agent/AGENTS.md`](instance/renovate-config/agent/AGENTS.md), a primary `renovate-coordinator` agent and the `frontend` subagent under [`instance/renovate-config/agent/.opencode/agents/`](instance/renovate-config/agent/.opencode/agents/). The coordinator keeps the workflow's task state, priority order, PR communication, fix-PR handoff, and merge/close decisions; the subagent cannot delegate. The legacy `CLAUDE.md` files and `personas/frontend/prompt.md` are legacy-only (Claude/Python runner) and stay for the transition — the existing KEDA deployments may still read them until offboarding; OpenCode never loads them, and cleanup happens after offboarding.

The profile locations are [`instance/ui-config/agent/instance.yaml`](instance/ui-config/agent/instance.yaml) and [`instance/renovate-config/agent/instance.yaml`](instance/renovate-config/agent/instance.yaml). The Renovate workflow is under [`instance/renovate-config/agent/workflows/renovate-fix/`](instance/renovate-config/agent/workflows/renovate-fix/); its `AGENTS.md` is the OpenCode guidance and its `CLAUDE.md` is the legacy-runtime version, kept legacy-only for the transition. For dispatcher behavior, see the submodule's [instance configuration](dev-bot/docs/presets/instance-config.md), [scheduling](dev-bot/docs/scheduling.md), and [deployment/rollback guide](dev-bot/docs/agent-dispatcher-deployment.md).

## Readiness gates before any cutover

1. **Dispatcher compatibility:** verify the dispatcher supports the required changes from Rehor #668, #674, #678, #679, #689, and #690, using the agreed source pin `b7bfd8b` — the current merged master tip: the Rehor #679 merge revision (`394edfd` plus the instance-env preflight unit: the profile's approved non-secret `env` reaches the registered TypeScript preflights as one read-only `instanceEnv` unit on the run context), followed by the additive merges #680 (Fabric Access TypeScript preflights), #681 (tier-2 Kubernetes Secret shorthand), #682 (UTF-8 encoding of the bot instance identity header, which this instance's non-ASCII identity relies on), #683 (Grype dependency patch), #688 (native delivery of profile-declared `sandbox.env`, which neither profile declares), #689 (the Renovate preflight port registering `renovate-discover` and `renovate-pr-status`), and #690 (constrained `sandbox.egress` destinations — strictly optional; neither profile declares any, so discovery output and sandbox behavior stay at the former baseline). Do not infer compatibility from a floating branch or image tag. A merged source revision is not a published image; gate 2 tracks publication separately. Dispatchers older than #689 reject the Renovate preflight IDs — the profile fails closed on them.
2. **Published dispatcher and runner images:** confirm published images compatible with the profiles and the `b7bfd8b` source exist. The deployed dispatcher image is built from rehor master `96d9e58`, which already contains #689 — both profiles' preflight IDs resolve on it, and the newer `b7bfd8b` pin adds only the optional egress feature, which neither profile uses; re-confirm the deployed revision at cutover time instead of trusting this document. The runner image referenced by both profiles (`quay.io/redhat-services-prod/console-next-tenant/nxtcm-ui-agent/nxtcm-ui-agent:latest`) must be confirmed compatible with the pinned source and the OpenCode runtime before cycles. A merged source revision must not be conflated with a published dispatcher or runner image. Image publication/promotion is a separate gate; this prep does not promote an image.
3. **Profile validation:** verify dispatcher discovery accepts both profiles, preserves the UI settings and schedule, resolves the UI preflights (`gh-pr-status`, `gl-mr-status`, `jira-sprint`) and the Renovate preflights (`renovate-discover` then `renovate-pr-status`) at the `b7bfd8b` pin, and renders both profiles' OpenCode configuration with the expected models (root `gpt-6.1-sol`; `frontend` subagent `rehor-openai/gpt-6.1-terra`). The Renovate profile is not silent: with actionable work its preflights produce scripts and dispatch a session; with no work `renovate-discover` returns `skip` and no sandbox launches.
4. **Tooling checks:** test the required MCP integration and npm setup against the candidate runner image — Node 24/Playwright, local Chromium, and the PatternFly and Chrome MCP servers — and record the results.
5. **Cycle checks:** verify a no-work UI cycle and a no-work Renovate cycle do not start a sandbox, then verify one representative UI cycle and one representative Renovate fix cycle (including fix-PR handoff behavior) behave as expected in an approved test/canary context. Confirm cycle and cleanup results before considering cutover. Before those cycles, confirm the stage model proxy allowlist (`OPENAI_ALLOWED_MODELS`) admits the selected models for both profiles (`gpt-6.1-sol` for each coordinator's primary session, `gpt-6.1-terra` for each frontend worker); the deployment config declares them, but a gateway allowlist denial fails the cycle closed.
6. **Bot-assigned candidate coverage and Jira gateway:** Rehor #678, contained in the pin, closes the parity gap: the dispatcher now feeds the deployment-provided Jira identity (`BOT_JIRA_EMAIL`) to the shared `jira-sprint`/`jira-kanban` preflights as the default bot-assigned fallback identity, and Rehor #679 generalizes the channel — the profile's whole approved non-secret `env` reaches those preflights as one read-only `instanceEnv` unit — so this profile deliberately declares no `with.email` (an explicit non-blank `with.email` would still take precedence, and a missing identity leaves the candidate search unassigned-only). Verify the fallback with a representative bot-assigned ticket and validate the live Jira gateway path end to end once a dispatcher image containing `96d9e58` is deployed.
7. **Screenshot upload (pre-cutover blocker):** Rehor #678, contained in the pin, wires the existing upload path: the dispatcher injects `GH_RELEASE_UPLOAD_URL` pointing at `/screenshots/upload` on the authenticated service gateway, the sandbox network policy admits only that POST route for the Python upload helper, and the helper authenticates with the supervisor-issued credential placeholder — never a raw token, and the legacy proxy host remains unreachable from a sandbox. No instance-level screenshot wiring exists or is needed. Verify an actual screenshot upload and the returned link in a representative visual UI cycle once a runner image containing `96d9e58` is deployed.
8. **Human review:** review GitOps diffs, identity/routing settings, schedule semantics, image references, and rollback readiness before changing any live deployment. The two-profile scope and the legacy KEDA interaction require explicit review.

Until every gate passes and an owner approves the cutover, leave live deployments untouched. Do not enroll either agent — UI or Renovate — in both legacy polling and dispatcher execution at once. For the Renovate entry this means the dispatcher-side cutover (config-repo enrollment and any replica-count change on the `nxtcm-ui-agent-renovate` app-interface entry) must be sequenced so legacy KEDA scaling and dispatcher scheduling never overlap.

## Rollback

If dispatcher execution must be stopped, remove this configuration repository from the dispatcher's configured repository list so neither profile is discovered. If the legacy UI or Renovate deployment was changed during an approved cutover, restore its previous GitOps deployment configuration, including its prior schedule, KEDA scaling, and identity. The retained legacy `CLAUDE.md` guidance, persona files, and Python preflight scripts support running the legacy runtime again without this branch's OpenCode files. Verify dispatcher discovery is gone and legacy execution is restored before declaring rollback complete. Do not modify the legacy template as part of this prep.
